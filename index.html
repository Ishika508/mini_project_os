Problem statement (Problem 3)

An intelligent traffic-control system collects data from road sensors, surveillance cameras and traffic signals. Incoming traffic information is queued for analysis, while signal-control tasks compete for CPU time and memory. Multiple processing tasks may require shared communication channels and monitoring resources.

Challenge: design a system that processes traffic data efficiently, synchronizes sensor-data production and consumption, manages memory for incoming data, and ensures safe resource allocation.

1 · CPU Scheduling

The CPU scheduler decides which ready process runs next. With one processor and many tasks, the policy determines how long each task waits and how responsive the system feels.

Metrics

Turnaround = Completion − Arrival
Waiting = Turnaround − Burst
Response = First run − Arrival

Algorithms

  • FCFS — run in arrival order; simple, but short tasks queue behind long ones (convoy effect).
  • SJF / SRTF — shortest (remaining) burst first; minimum average waiting time, risk of starving long tasks.
  • Priority — lowest number = most urgent; preemptive variant interrupts a running task. Aging avoids starvation.
  • Round Robin — fixed time quantum, circular queue; fair and responsive, more context switches.
In the traffic system: an emergency-vehicle preemption task must run before routine report generation, so priority scheduling is natural; Round Robin keeps camera analytics from starving sensor aggregation.

2 · Process Synchronization — Producer–Consumer

Producers insert items into a shared bounded buffer; consumers remove them. Without coordination, threads may overwrite unread data, read empty slots, or corrupt the buffer indices (a race condition).

Semaphore solution

empty = N (free slots) full = 0 (filled slots) mutex = 1
Producer: wait(empty) → wait(mutex) → insert → signal(mutex) → signal(full)
Consumer: wait(full) → wait(mutex) → remove → signal(mutex) → signal(empty)
  • empty / full counting semaphores block producers on a full buffer and consumers on an empty one.
  • mutex gives mutual exclusion over the buffer pointers.
  • Order matters: taking mutex before empty/full can deadlock — a sleeper holds the lock the other side needs. The simulator has a switch to demonstrate this.
In the traffic system: loop detectors and cameras are producers of data packets; analytics workers are consumers. The buffer absorbs bursts, and back-pressure (a blocked sensor) is visible when the CPU cannot keep up.

3 · Deadlock Avoidance — Banker's Algorithm

Deadlock needs mutual exclusion, hold-and-wait, no preemption and circular wait. Avoidance lets the OS grant a request only if the resulting state is safe: some order exists in which every process can finish.

Data structures (n processes, m resource types)

Available[m] Max[n][m] Allocation[n][m]
Need[i][j] = Max[i][j] − Allocation[i][j]

Safety algorithm

  • Work = Available; Finish[i] = false for all i.
  • Find i with Finish[i] = false and Need[i] ≤ Work. If none → go to the last step.
  • Work += Allocation[i]; Finish[i] = true; repeat.
  • If all Finish[i] are true the state is safe, and the order found is a safe sequence.

Resource-request algorithm

Request ≤ Need? Request ≤ Available? Then pretend to allocate and run the safety algorithm; grant only if safe, otherwise make the process wait.

In the traffic system: communication channels, camera decoders and signal-controller links are shared by analytics tasks. Two camera tasks each holding one decoder and needing another would deadlock — Banker's refuses the second admission.

4 · Memory Management

Contiguous allocation gives each process one block of main memory. The OS tracks free holes and chooses one for every request.

Partitioning

  • Fixed — memory pre-divided into blocks; one process per block; wastes space inside a block (internal fragmentation).
  • Variable (dynamic) — blocks are carved to the exact request size; freed neighbours merge; leaves scattered holes (external fragmentation).

Placement strategies

  • First Fit — first hole big enough: fast.
  • Best Fit — smallest hole big enough: tiny leftovers, slower search.
  • Worst Fit — largest hole: leftovers stay usable, but big holes vanish quickly.
Internal = block size − process size
External = total free − largest hole (free space unusable for a large request)

Compaction slides allocated blocks together to merge all holes into one.

In the traffic system: every analysis task needs a working buffer (sensor window, camera frame cache). If no hole is big enough, the task waits even though enough total memory is free — fragmentation in action.

How the four mechanisms work together

  1. Producers → buffer (synchronization). Each sensor/camera creates a packet and inserts it with wait(empty) · wait(mutex). If the buffer is full the sensor blocks — back-pressure.
  2. Consumers → tasks. An idle analytics worker removes a packet and creates an OS task whose burst, priority and memory need depend on the packet (emergency > sensor > camera).
  3. Memory management. The task asks for a block using the chosen fit strategy. No hole ⇒ it waits in the admission queue.
  4. Banker's algorithm. The task declares its maximum claim on channels, decoders and signal links and requests them in two stages. A request that would leave an unsafe state is delayed, so the system never deadlocks.
  5. CPU scheduling. Admitted tasks enter the ready queue; the scheduler picks one per time unit. Completed tasks release memory and resources and update the signal controller.
  6. Feedback. Fresher analysis → better green times and emergency preemption → shorter queues → different sensor readings. A slow OS pipeline therefore directly costs drivers time.
